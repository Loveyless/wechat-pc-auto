# Plan：主链正确性收口与 Tk 回退下线

## 任务概述

当前仓库的打包链、桌面壳发布闸口和 Windows 打包 smoke 已经基本成型。
下一阶段不该继续把精力砸在“能不能再打一个包”，而该收口主链 correctness、CI 反馈速度、配置契约一致性，以及旧 Tk 回退路径的维护负担。

本计划覆盖四类工作：

- 修正后端健康契约，避免桌面壳和 smoke test 建立在假健康之上
- 增加快速回归 CI，把逻辑回归和重量级打包回归分开
- 收敛配置 schema 和加载校验逻辑，减少重复实现
- 下线旧 Tk 回退路径，删除已经不再属于正式产品边界的代码和打包链

## 当前仓库事实

- 当前主路径已经是 `listener_app/backend_main.py + desktop-shell/`，不是 Tk 侧边栏：
  - `README.md`
  - `docs/desktop-shell-build.md`
- 旧 Tk 路径 `listener_app/sidebar_translate_listener.py` 仍然存在，并且仍被文档和旧打包脚本引用：
  - `README.md`
  - `docs/windows-packaging.md`
  - `config/listener.md`
  - `scripts/build_windows_exe.ps1`
- GitHub Actions 现在只有一条 Windows 打包/发布烟测：
  - `.github/workflows/windows-packaging-smoke.yml`
  - 这条 workflow 当前仍会执行 `scripts/build_windows_exe.ps1`
- `/healthz` 当前返回固定 JSON：
  - `listener_app/runtime_api.py` 在 `/healthz` 上直接返回 `{"status": "ok"}`
- 桌面壳和 release smoke 把 `/healthz` 当成 backend ready 信号：
  - `desktop-shell/src-tauri/src/backend_health.rs`
  - `desktop-shell/src-tauri/src/backend/bootstrap.rs`
  - `scripts/smoke_desktop_shell_release.py`
- 当前 `/healthz` 不读取 runtime 实际状态，也不区分：
  - backend 正在启动
  - backend 已健康
  - backend 启动失败
  - backend 已降级但 HTTP 线程还活着
- 当前 `backend_main.py` 的启动顺序是先 `service.start()`，再 `api_server.start()`：
  - 这意味着一旦 backend runtime 在启动阶段直接抛错，HTTP 层根本不会起来
  - 所以现状下不可能通过 `/healthz` 对外暴露 `startup_failed`
- 配置加载/校验逻辑存在重复：
  - 新主路径：`listener_app/backend_runtime.py`
  - 旧 Tk 路径：`listener_app/sidebar_translate_listener.py`
  - provider 私有配置：`listener_app/sidebar_tts.py`
- 旧 Tk 路径不是“无成本保留”：
  - `listener_app/sidebar_translate_listener.py` 865 行
  - `listener_app/sidebar_ui.py` 762 行
  - `tests/test_sidebar_listener_helpers.py` 1527 行
  - 它们会持续放大维护面和配置/行为重复
- Tk 相关测试当前不是独立分层：
  - `tests/test_sidebar_listener_helpers.py` 同时加载并测试 `sidebar_translate_listener`、`sidebar_shared`、`sidebar_translate_runtime`、`sidebar_runtime_support`、`sidebar_tts`、`sidebar_ui`
  - 这意味着 Tk 下线前必须先拆测试，不能把这份测试文件整份直接删掉
- `listen.targets` 当前已经是分叉语义：
  - 新主路径不再依赖它决定监听范围
  - 旧 Tk 路径仍把它当 target 入口和运行时编辑对象
  - 所以“统一 schema”不能等价于“继续保留 Tk 语义为主路径服务”

## 目标

- 让桌面壳 bootstrap、release smoke 和 CI 都依赖真实健康状态，而不是“HTTP 进程没死”
- 让 PR 反馈分成“快回归”和“重烟测”两层，避免所有回归都等 Windows 打包
- 让配置 schema 有单一实现来源，不再同时维护两条主链的同义逻辑
- 正式删除旧 Tk 回退路径及其打包链，收窄产品边界

## 不做的事

- 不新增 TTS provider 或翻译 provider
- 不扩展旧 Tk UI 任何新能力
- 不把旧 Tk 重新包装成“正式降级路径”
- 不把密钥或 `.env.local` 烘焙进交付产物

## 为什么 Tk 回退值得删除

结论先说死：值得删，而且应该删。

原因不是“看着不顺眼”，而是它已经在制造真实维护成本：

- 产品主路径已经不是 Tk，继续保留它，只会让文档、配置、测试、打包和 CI 都多维护一套影子实现
- `backend_runtime.py` 和 `sidebar_translate_listener.py` 明显存在重复的配置读取与运行时拼装逻辑；只要再改一次配置契约，就有再次漂移的风险
- 旧 Tk 打包脚本 `scripts/build_windows_exe.ps1` 还在 CI 里运行，这会把“已经不是主交付”的链路继续抬成强约束
- 旧 Tk 文档还在，团队很容易继续把它当“保险 fallback”，这会直接把产品边界写坏

但删除方式不能糙。不能今天一句“删 Tk”，明天直接把文件砍掉。
必须先让替代路径和验证口径足够硬，再删除旧链路；否则就是用更少的代码，换更多的盲区。

## 优先级与阶段

### P0：把 `/healthz` 从假健康改成真健康

#### 问题

当前 `/healthz` 只证明 `RuntimeApiServer` 的 HTTP handler 活着，不证明 backend runtime 已完成启动，更不证明 worker 已进入可用状态。
这会让下面三件事同时失真：

- Tauri 壳 bootstrap 的 ready 判定
- `scripts/smoke_desktop_shell_release.py` 的 smoke 结论
- CI 的 release smoke 通过含义

#### 目标

- `/healthz` 至少能区分 `starting`、`ok`、`startup_failed`、`degraded`
- 桌面壳只把真正健康的状态视为 ready
- smoke test 失败时能明确知道是“HTTP 没起来”还是“HTTP 起了但 runtime 没健康”

#### 建议改动

- 扩展 `listener_app/runtime_api.py` 的 `/healthz` 返回，基于 runtime 实际状态输出结构化健康结果
- 在 `listener_app/backend_runtime.py` 中定义可复用的健康状态映射，而不是散着判断
- 明确启动顺序改造，至少二选一，不允许继续含糊：
  - 先启动 API 壳层，再驱动 backend runtime 启动，让 `/healthz` 能报告 `starting/startup_failed`
  - 或者捕获 `service.start()` 的启动异常并持有可查询状态，再由 HTTP 层对外暴露
- 不接受“继续先 `service.start()`，但文档里假装 `/healthz` 能返回 `startup_failed`”这种伪方案
- 更新：
  - `desktop-shell/src-tauri/src/backend_health.rs`
  - `desktop-shell/src-tauri/src/backend/bootstrap.rs`
  - `scripts/smoke_desktop_shell_release.py`
- 为 `/healthz` 增加 Python 单测和 Rust 侧解析单测

#### 最小验证

- `python -m unittest tests.test_runtime_api`
- `cd desktop-shell/src-tauri && cargo test`
- `python scripts/smoke_desktop_shell_release.py`

### P0：补一条快速回归 CI

这条 workflow 太重，导致“逻辑回归”和“打包回归”被绑死在一起，反馈慢，而且定位脏。

#### 目标

- PR 上先拿到快反馈，再跑重 smoke
- 把“代码逻辑坏了”和“Windows 打包环境坏了”分开

#### 建议改动

- 新增一条 lightweight CI，例如 `runtime-fast-checks.yml`
- 只跑：
  - Python 单测
  - `desktop-shell` 前端测试
  - `desktop-shell` 前端构建
  - Rust 单测
- 现有 `windows-packaging-smoke.yml` 继续保留，但只承担 release 级烟测

#### 最小验证

- 本地对应命令全部可跑
- 首轮 GitHub Actions 成功执行

### P1：统一配置 schema 和加载/校验入口

#### 问题

同一批配置语义现在散在多处：

- `listener_app/backend_runtime.py`
- `listener_app/sidebar_translate_listener.py`
- `listener_app/sidebar_tts.py`
- `config/listener.md`

这不是“代码风格问题”，是实打实的一致性风险。

#### 目标

- 配置字段、默认值、校验逻辑有一个代码层单一来源
- 文档跟着这份来源走，不再靠人肉同步
- 为删除 Tk 路径提前拔掉重复逻辑

#### 建议改动

- 提炼统一配置模型/加载模块，例如：
  - `listener_app/runtime_config.py`
- 先定义“主路径存活语义”的 schema，把当前正式交付路径需要的字段、默认值和校验收口到一处
- Tk 删除前如果还需要兼容旧入口，只允许保留最小适配层；禁止把 Tk 专属语义反向抬进主链
- 特别是 `listen.targets` 这类已经分叉的字段，要明确：
  - 主路径只保留它作为配置快照或兼容字段时的受限语义
  - 不再为了照顾 Tk 回退，把 target 编辑模型重新绑回主链
- 收敛这些字段的默认值与校验：
  - `listen.interval_seconds`
  - `listen.load_retry_seconds`
  - `listen.session_preview_dedupe_window_seconds`
  - `translate.*`
  - `display.tts_auto_read_active_chat`
  - `tts.provider` 与 provider 私有 `config_path`
- 同步更新：
  - `config/listener.md`
  - `README.md`
  - `docs/wechat-listening-pitfalls.md`

#### 最小验证

- `python -m unittest`
- 手工核对文档示例与运行时默认值一致

### P1：下线旧 Tk 回退路径

#### 问题

旧 Tk 路径已经不再属于正式主路径，却还占着：

- 代码
- 测试
- 文档
- 打包脚本
- CI 时间

这不是冗余备份，而是长期分叉。

#### 目标

- 彻底从主仓库交付链里移除 Tk UI 路径
- 清掉旧 Tk 打包、旧 Tk 文档入口、旧 Tk CI 依赖
- 把“开发回退”改成“源码态 backend + desktop-shell dev”这条真实还在维护的路径

#### 删除边界

先做测试拆分，再做 Tk 删除。

应删除：

- `listener_app/sidebar_translate_listener.py`
- `listener_app/sidebar_ui.py`
- 拆分后仅服务于 Tk UI 的测试
- `scripts/build_windows_exe.ps1`
- `docs/windows-packaging.md`
- 所有把 Tk 当可运行入口的 README/配置说明

应保留并检查是否仍被新主路径使用：

- `listener_app/sidebar_translate_runtime.py`
- `listener_app/sidebar_runtime_support.py`
- `listener_app/sidebar_tts.py`
- `listener_app/sidebar_shared.py`
- `listener_app/group_listener_worker.py`

#### 测试拆分要求

- 先把 `tests/test_sidebar_listener_helpers.py` 拆成按职责分层的测试：
  - shared/config helper
  - translate runtime
  - runtime support
  - TTS/provider config
  - Tk UI 专属行为
- 只有在共享测试已经迁出后，才允许删除 Tk UI 专属测试
- 不接受“Tk 要删，所以把混装测试整份删掉”这种偷懒做法；那会把仍在主路径里使用的 helper 覆盖一起删没

#### 前置条件

- `/healthz` 真健康已经落地
- 快速回归 CI 已经接管主路径逻辑验证
- 新主路径配置 schema 已统一
- `backend_main.py + desktop-shell` 的开发/排障文档已经完整

#### 最小验证

- 删除 Tk 路径后：
  - `python -m unittest`
  - `cd desktop-shell && npm test`
  - `cd desktop-shell && npm run build`
  - `cd desktop-shell/src-tauri && cargo test`
  - `python scripts/build_desktop_shell_sidecars.py --python python`
  - `python scripts/smoke_desktop_shell_release.py`
- `.github/workflows/windows-packaging-smoke.yml` 不再依赖旧 Tk 打包脚本

## 推荐执行顺序

1. `/healthz` 真健康
2. 快速回归 CI
3. 配置 schema 收敛
4. Tk 回退下线
5. `.editorconfig`

这个顺序不是随便排的。
先修健康契约，是因为现在的 smoke 结论含义都不够硬。
先补快 CI，是因为删 Tk 之前要先保证主路径有快反馈。
先收配置 schema，是因为 Tk 下线前要先拔掉重复逻辑，但这里要按主路径语义收口，不能反向保留 Tk 包袱。
Tk 删除放在这之后，才不是瞎砍。

## 迁移 / 回滚 / 降级策略

- 任何阶段只要影响主路径 correctness，就先阻断分发，不接受“先合了再说”
- Tk 删除前，如果主路径回归，允许临时回退到：
  - `python listener_app/backend_main.py --config .\config\listener.json`
  - `cd desktop-shell && npm run dev`
  - 或 `npm run tauri dev`
- Tk 删除后，不再保留 `sidebar_translate_listener.py` 作为官方回退
- 如果团队仍然需要历史参考，允许把 Tk 代码移到独立 archive 分支，但不应继续挂在主仓库交付链里

## 交付标准

满足以下条件，才算本计划完成：

- `/healthz` 语义真实，桌面壳 ready 判定不再建立在假健康上
- GitHub Actions 同时具备快回归和重烟测两层反馈
- 配置 schema 只有一套主实现来源
- 主仓库中不再保留 Tk UI 路径和旧 Tk 打包链
- README / `config/listener.md` / `docs/wechat-listening-pitfalls.md` 与实际代码边界一致
