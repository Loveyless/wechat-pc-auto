# Plan：微信自动监听前后端分离与 Tauri 界面改造

## 任务概述

本阶段目标是把当前基于 Tk 的桌面展示层替换为 `React + Tauri + shadcn/ui`，同时把现有 Python 监听主流程拆成可独立运行的本地后端服务。  
后端继续保留 Python，并允许为前后端分离、状态管理、`HTTP + WebSocket` 通信做结构调整；但不重写 UIA 核心、不修改核心翻译/TTS provider、不做跨平台、不做云同步。

## 当前仓库事实

- 当前展示层是 Tk：`listener_app/sidebar_ui.py`
- 当前主入口同时承担 UI、编排、事件处理：`listener_app/sidebar_translate_listener.py`
- 当前监听 worker 单独进程通过 stdout 输出 JSON 事件：`listener_app/group_listener_worker.py`
- 当前运行时辅助逻辑负责拉起 worker、读取 stdout、转入队列：`listener_app/sidebar_runtime_support.py`
- 仓库已有文档明确指出“监听和 UI 必须分离”：`docs/wechat-listening-pitfalls.md`

当前链路本质上是：

```text
UIA/worker -> stdout JSON -> Python 主进程队列 -> Tk UI 刷新
```

这条链路可跑，但问题也很明显：

- 展示层是 Tk，界面能力弱，扩展成本高
- 主入口职责过多，不是前后端分离结构
- 事件管道只够当前 Tk 使用，不适合现代前端直接消费

## 已确认范围

### 本阶段要做

- 保留 Python 后端，但按“本地后端服务”重构边界
- 前端改为 `React + Tauri + shadcn/ui`
- 前后端通信固定为：**本地 HTTP + WebSocket**
- 第一版 UI 必须包含：
  - 会话列表
  - 消息流主面板
- 保留实时翻译展示
- 保留 TTS 自动播放
- 保留微信 UIA 监听能力
- 监听目标从“多 target”调整为：**左侧会话列表全量监听（群聊 + 私聊）**
- 前端展示方式固定为：**按会话分组，点击会话查看消息流**

### 本阶段不做

- 不重写 UIA 为 Rust
- 不做跨平台
- 不修改核心翻译 provider / TTS provider
- 不先做云同步、账号系统、远程协作
- 不保留旧 Tk 作为 fallback
- 不要求兼容现有配置文件格式；允许重新设计配置
- 不把“安装分发方案”纳入本阶段交付范围

## 关键定义

### 1. “左侧会话全量监听”的产品定义

本阶段目标不是“只监听手工选中的 target”，而是：

- 监听微信左侧会话列表中的**群聊和私聊**
- 只要会话出现新消息或预览变化，就进入统一事件流
- 前端会话列表展示所有被采集到的会话
- 前端点击会话后，主面板展示该会话对应的消息流

### 2. Phase 1 的真实交付边界

本阶段只交付：

- 架构拆分方案
- 前后端职责边界
- 前端 UI 方案
- 事件/接口方案
- 可实施的分阶段任务拆分

本阶段**不把安装包方案当作交付目标**。  
“分发体验差”是已知痛点，但不应在本阶段和架构/UI 改造绑死，否则范围会失控。

## 目标架构

### 后端（Python）

后端职责只保留对桌面运行真正必要的部分：

- 微信 UIA 监听
- 监听 worker 生命周期管理
- 消息采集与会话状态聚合
- 翻译调用与结果写回
- TTS 自动播放协调
- 本地配置读写
- 对前端暴露本地 HTTP + WebSocket

后端不再负责：

- Tk 界面渲染
- 直接驱动桌面文本控件更新
- 针对 Tk 的队列刷新逻辑

### 前端（React + Tauri + shadcn/ui）

前端职责：

- 渲染会话列表
- 渲染消息流主面板
- 维护会话切换与筛选状态
- 展示连接状态 / 翻译状态 / 基础运行状态
- 通过 HTTP 读取初始化状态
- 通过 WebSocket 接收实时事件

前端不直接接触：

- UIA
- 微信窗口句柄
- Python worker 内部实现

### 通信方式

固定为本地 `HTTP + WebSocket`：

- `HTTP`：初始化状态、配置读取/更新、显式命令
- `WebSocket`：新消息、会话更新、翻译结果、播放状态、错误事件

不采用：

- Tk 内部队列直接绑定前端
- 前端直接读 Python 子进程 stdout
- 先做 sidecar 私有 IPC 再补 HTTP/WS

原因很直接：  
`HTTP + WebSocket` 更稳、更可观察、更适合 React/Tauri，也更利于后续继续拆分。

## 推荐接口边界

### HTTP（建议）

- `GET /api/state`
  - 返回当前运行状态、连接状态、前端初始化所需基础信息
- `GET /api/sessions`
  - 返回当前已发现会话列表
- `GET /api/config`
  - 返回当前配置快照
- `PUT /api/config`
  - 更新配置
- `POST /api/runtime/restart`
  - 重启后端监听主流程

### WebSocket 事件（建议）

- `session.upsert`
  - 会话新增或状态更新
- `message.created`
  - 新消息进入统一事件流
- `translation.updated`
  - 翻译结果更新
- `tts.state`
  - TTS 播放状态变化
- `backend.state`
  - 后端连接 / 监听状态变化
- `error`
  - 可展示错误事件

## 关键设计决策

### 决策 1：后端保留 Python，但必须服务化

不是单纯“换个前端壳”，而是要把现在的 Python 主流程拆成真正可被前端消费的本地服务。  
这意味着：

- 要抽离 Tk 依赖
- 要重做事件出口
- 要明确会话 / 消息 / 状态的数据模型

### 决策 2：不保留 Tk fallback

本阶段直接替换，不走双轨。  
这样做的好处是范围清楚，不会长期维护两套 UI。  
坏处是切换风险更高，所以验收标准必须更硬。

### 决策 3：配置允许重定

本阶段允许重新设计配置结构，不强行兼容旧配置。  
否则前后端拆分时会被历史字段和 Tk 特化逻辑拖住。

### 决策 4：UI 第一版只做两块核心区域

第一版只做：

- 会话列表
- 消息流主面板

日志面板、复杂设置面板、托盘等都不进入第一版核心范围。  
这不是缺功能，而是控制阶段边界。

## 关键风险

### 风险 1：左侧会话“全量监听”的技术口径可能和当前实现不一致

当前系统已经有 chat/session/mixed 等监听模式，但“左侧会话列表全量监听”不是一句 UI 需求就能自动成立。  
必须明确区分：

- 左侧会话预览文本能拿到什么
- 已打开会话正文能拿到什么
- 群聊与私聊的事件完整度是否一致

这部分要在设计阶段单独定义消息模型，不能把“预览事件”和“完整正文消息”混成一种。

### 风险 2：不保留 Tk fallback，切换窗口会更陡

由于不保留旧 Tk 作为过渡，新的前后端链路必须一次打通：

- 后端能独立跑
- 前端能收到初始化状态
- WebSocket 能稳定推送
- 会话切换和消息流能稳定展示

否则替换会直接失败。

### 风险 3：本阶段不做打包方案，分发痛点不会被本阶段彻底解决

这不是遗漏，是范围控制。  
必须在文档里明确：本阶段解决的是**架构和 UI**，不是分发闭环。

## 分阶段执行计划

### Phase 1：梳理现状与数据模型

- 拆清当前链路中的会话、消息、翻译、TTS、状态事件
- 区分“会话预览事件”和“完整消息事件”
- 明确前端初始化需要的最小状态模型

产出：

- 后端领域对象草案（session/message/runtime state）
- WebSocket 事件草案
- HTTP 初始化接口草案

### Phase 2：抽离 Python 后端服务边界

- 从 `sidebar_translate_listener.py` 中拆出 UI 无关逻辑
- 保留 UIA / worker / 翻译 / TTS 核心能力
- 建立统一状态存储与事件分发出口

产出：

- 可独立运行的本地后端主入口
- 面向前端的事件总线 / 状态层

### Phase 3：建立 HTTP + WebSocket 通信层

- 提供初始化状态读取
- 提供会话列表读取
- 提供实时事件推送
- 保证事件命名和 payload 稳定

产出：

- API 路由草案
- WebSocket 事件契约
- 最小 smoke test 方案

### Phase 4：搭建 Tauri + React + shadcn/ui 前端骨架

- 建立桌面壳
- 建立会话列表和消息流主面板
- 接入初始化拉取与实时 WS 更新
- 完成基础状态展示

产出：

- 前端目录结构
- 会话列表页面
- 消息流主面板

### Phase 5：切换到“全量会话监听”工作流

- 以统一事件流消费左侧会话列表变化
- 前端按会话分组展示
- 点击会话切换消息流
- 保持实时翻译展示与 TTS 自动播放语义

产出：

- 会话聚合逻辑
- 会话切换逻辑
- 消息渲染链路

### Phase 6：移除 Tk 主路径并更新文档

- 去掉 Tk 作为主运行路径
- 更新启动方式、配置说明、运行说明
- 明确新的前后端边界

产出：

- 新启动入口说明
- 新配置说明
- 迁移说明

## 最小验收标准

满足以下条件，才算本阶段设计和实施边界成立：

1. Python 后端可以在无 Tk 依赖的前提下独立运行
2. 前端可以通过 HTTP 拉到初始化状态
3. 前端可以通过 WebSocket 收到会话和消息更新
4. 会话列表可展示群聊和私聊
5. 点击会话后，主面板可展示该会话的消息流
6. 实时翻译展示保留
7. TTS 自动播放行为保留
8. 主运行路径不再依赖旧 Tk UI
