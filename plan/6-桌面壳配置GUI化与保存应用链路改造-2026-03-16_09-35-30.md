# Plan: 桌面壳配置 GUI 化与保存/应用链路改造

## 背景与动机
当前 DeepLX 与腾讯云 TTS 已经接入主链路，但用户仍只能直接编辑 `config/*.json`。问题不在于“前端少几个输入框”，而在于配置读取、配置保存、配置应用、secret 处理和托管 sidecar 的 ownership 还没形成闭环。  
如果现在只补一个设置页，不补后端契约和应用策略，结果只会是“看起来能改、实际上没生效”的假配置页。
<!-- 下游：proposal.md 的 motivation -->

## Goal
- 为桌面壳提供正式的配置入口，覆盖当前主链路实际受支持的翻译配置、显示配置和 TTS provider 配置。
- 第一版设置页覆盖当前代码里所有已支持的 TTS provider，而不是只做腾讯云单分支；至少包括 `windows_system`、`doubao`、`tencent_cloud`。
- 建立“读取当前可编辑配置 -> 校验 -> 原子保存 -> 明确告知是否已生效”的闭环，不再要求用户手改 JSON。
- 第一阶段明确采用“保存配置”和“应用配置”分离策略：
  - 开发态或非托管态：保存后提示手动重启 backend
  - Tauri 托管且 shell 真正拥有 backend sidecar：允许保存后重启 managed backend sidecar，使新配置生效
<!-- 下游：proposal.md 的 scope -->

## Non-goals
- 不做 backend 进程内的 translator / TTS player 热重载。
- 不把 `tts` provider 私有参数重新塞回 `listener.json`。
- 不把 `.env.local` 做成完整 GUI 编辑器。
- 不把前端局部显示态，例如“原文开关”“状态面板展开状态”，混进持久化配置。
- 不把当前进行中的桌面壳视觉层重构 change 偷带成“顺手加设置页”。

## 约束
- 第一阶段不做 backend 进程内热重载；translator 和 TTS player 仍按“重建 runtime / 重启 sidecar 后生效”的模型处理。
- `listener.json` 与 TTS provider 私有 JSON 的边界不能破；provider 私有参数继续独立存放。
- secret / 类 secret 字段允许在 GUI 中直接输入并提交到 backend，但不能原文回显到前端；`GET /api/config` 只返回来源与是否已配置，`PUT /api/config` 采用 write-only 更新。
- 保存逻辑必须原子写、保留未知字段，并保持 LF。
- GUI 不能绕过现有 fail-fast 校验；配置入口变了，约束不能变松。
- managed apply 不能杀掉外部 backend；只有当前 shell 真正拥有的 sidecar child 才允许重启。
- `/healthz`、`/api/runtime`、`/api/sessions`、`/events` 现有语义不能因为配置页顺手漂移。
- 当前正在进行的 `refactor-desktop-shell-visual-system` 仍保持 presentation-only；本计划不能把它的视觉改造和本次配置契约改造混成一个 change。

## 验收标准
1. 当用户在桌面壳打开设置入口时，前端能够读取一份完整、安全、可编辑的配置 DTO，而不是当前残缺的 `/api/config` 快照；secret 字段只展示“是否已配置/来源/env key”，不回显原值。
2. 当用户切换 TTS provider 时，设置页能为当前代码里所有已支持 provider 提供正确的表单分支；`windows_system`、`doubao`、`tencent_cloud` 都不会出现“可选但不可配”的半残状态。
3. 当用户提交合法配置到 backend 时，`listener.json` 与 provider 私有 JSON 会按各自边界被原子写入运行时目录，且未知字段不会被误删。
4. 当用户在 GUI 中直接填写 DeepLX URL、`secret_id`、`secret_key` 或同类敏感值并保存后，backend 能写入配置文件或对应 provider 配置文件，但后续 `GET /api/config` 仍不会回显这些原值。
5. 当用户提交非法配置时，API 返回字段级校验错误，现有配置文件保持不变，前端能显示失败原因。
6. 当用户在开发态或非托管态保存配置时，前端明确显示“已保存，需手动重启 backend 才生效”；运行态行为在 backend 重启前不变。
7. 当用户在 Tauri 托管且 shell 拥有 backend sidecar 的场景下执行“保存并应用”时，配置文件先保存，再由桌面壳重启 managed backend sidecar；桌面壳在不关闭主窗口的前提下重新连接并体现新配置。
8. 当桌面壳连接的是复用来的 backend 或外部 backend 时，不允许执行会杀进程的 apply；前端必须降级为“仅保存 + 提示手动重启”。
9. 现有 header 运行态“朗读开关”仍可用，并且不会偷偷改写设置页里的持久化默认值；设置页里的 `tts_auto_read_active_chat` 表达的是启动默认值，不是即时运行态。
10. `config/listener.md` 与 `docs/wechat-listening-pitfalls.md` 会和新契约同步更新，避免出现“界面能配、文档还说只能手改 JSON”的回归。

## 验证方式
- Python 回归：
  - 为配置 DTO / 保存逻辑补单测
  - 覆盖 secret masking、env source 标记、直接填密钥后的 write-only 行为、未知字段保留、provider 分文件写入、非法值 fail-fast
- 前端回归：
  - `cd desktop-shell && npm test`
  - 覆盖 settings hydrate、dirty state、保存成功/失败、managed / unmanaged 两种 CTA 分支、三个 TTS provider 的表单分支
- Rust 回归：
  - `cd desktop-shell/src-tauri && cargo test`
  - 覆盖 managed restart 只允许 owned child、marker 清理与重启路径稳定
- 构建回归：
  - `cd desktop-shell && npm run build`
- 手工开发态：
  1. `python listener_app/backend_main.py --config ".\\config\\listener.json"`
  2. `cd desktop-shell && npm run dev`
  3. 通过设置页保存配置
  4. 观察 `config/*.json` 已更新，但前端明确提示“需手动重启 backend”
  5. 重启 backend 后确认新配置生效
- 手工托管态：
  1. `cd desktop-shell && npm run tauri dev`
  2. 通过设置页执行“保存并应用”
  3. 观察 backend sidecar 被重启、`/healthz` 重新 ready、前端自动恢复连接
  4. 确认 `%LOCALAPPDATA%\\com.wechatauto.shell\\config\\` 下配置已更新

## 迁移 / 回滚 / 降级
- 数据迁移：N/A。第一阶段只围绕现有已支持字段做 GUI 化与配置契约化，不引入必须迁移的持久化 schema。
- 回滚策略：
  - 回滚前端设置入口、配置 API 和 Tauri restart 命令
  - 保持 `listener.json` 与 provider 私有 JSON 的现有字段兼容，不把 rollout 建立在新 schema 必需项之上
- 降级策略：
  - 如果 managed backend restart 不稳定，优先降级成“托管态也只保存并提示重开应用”，而不是硬保“保存并应用”
  - 如果 secret 处理实现不完整，禁止先上线明文回显版本；宁可先只支持显示来源状态与 write-only 更新
