# Plan: 桌面壳配置 GUI 化与保存/应用链路改造

## 背景与动机

当前 DeepLX 与腾讯云 TTS 已经接入主链路，但配置入口仍停留在手改 JSON。
这不是“前端少几个输入框”的问题，而是配置读取、配置保存、配置应用、secret 处理和运行时 ownership 都没有形成闭环。

如果直接在前端拼一个设置页，不补后端契约和应用策略，只会得到一套看起来能改、实际上不生效或重启就丢的假配置页。

## Goal

- 为桌面壳提供一套正式配置入口，覆盖当前主链路真正受支持的翻译/TTS 配置，不再要求用户直接编辑 JSON 文件。
- 建立“读取当前可编辑配置 -> 校验 -> 原子保存 -> 明确告知是否已生效”的闭环，避免“保存成功但运行态没变”的假象。
- 明确区分三类状态：
  - 持久化配置
  - 运行态临时开关
  - secret / 环境变量来源
- 第一阶段采用稳妥策略：
  - 不做 backend 进程内热重载
  - 开发态/非托管态保存后提示手动重启 backend
  - Tauri 托管且 shell 拥有 sidecar 时，允许“保存并应用”通过重启 managed backend sidecar 生效

## Non-goals

- 不做 translator / TTS player 的进程内热切换；这条路现在风险高、收益低。
- 不把 `tts` provider 私有字段重新塞回 `listener.json`；继续保持独立 JSON。
- 不在第一阶段把 `.env.local` 做成完整 GUI 编辑器。
- 不把前端局部显示态，例如“原文开关”“状态面板展开状态”，混进持久化配置。
- 不扩展新的翻译 provider、TTS provider、发送消息能力或多实例壳行为。

## 当前仓库事实

- backend 配置在启动时一次性加载。`load_runtime_config()` 负责解析 `listener.json`，`load_backend_settings()` 里立刻创建 translator 和 TTS player，而 `BackendRuntimeService.start()` 只在启动阶段调用一次：`listener_app/runtime_config.py:109`、`listener_app/backend_runtime.py:219`、`listener_app/backend_runtime.py:359`。
- 当前 HTTP API 没有配置保存契约。`RuntimeApiServer` 仅提供 `/healthz`、`/api/runtime`、`/api/sessions`、`/api/config`，以及两个 POST：`/api/runtime/active-session`、`/api/runtime/tts-auto-read`：`listener_app/runtime_api.py:103`、`listener_app/runtime_api.py:136`、`listener_app/runtime_api.py:150`、`listener_app/runtime_api.py:165`。
- `/api/config` 只是残缺快照，不是完整可编辑配置。当前只返回部分 `listen`、`translate.enabled/provider`、`display.english_only/tts_auto_read_active_chat`、`tts.provider/available` 和 `runtime.config_path`，没有 `deeplx_url`、语言参数、超时、`tts.config_path`、腾讯云 provider 私有参数等：`listener_app/backend_runtime.py:318`。
- 现有“朗读开关”只是运行态 toggle，不落盘。`set_tts_auto_read_enabled()` 只改内存中的 `settings` 和 runtime state，重启后仍回到文件配置：`listener_app/backend_runtime.py:298`。
- 前端并未消费 `/api/config`。当前只请求 `/api/runtime`、`/api/sessions`、`/api/sessions/:id/messages`，以及运行态 `tts-auto-read` 切换：`desktop-shell/src/lib/api.ts:63`、`desktop-shell/src/lib/api.ts:67`、`desktop-shell/src/lib/api.ts:72`、`desktop-shell/src/lib/api.ts:85`。
- `useDesktopShell()` 的 hydrate 入口只依赖 snapshot + sessions；桌面壳 header 目前只有“会话栏开关 / 原文开关 / 朗读开关 / 状态面板开关”，没有配置入口：`desktop-shell/src/hooks/use-desktop-shell.ts:172`、`desktop-shell/src/components/shell/desktop-shell.tsx:114`。
- DeepLX URL 既可以来自配置，也可以来自环境变量 `DEEPLX_URL`：`listener_app/runtime_config.py:145`。
- TTS secret 既支持直接写在 provider 配置 JSON，也支持通过 `*_env` 指定环境变量；读取逻辑由 `read_secret_config_value()` 收口：`listener_app/sidebar_tts.py:102`、`listener_app/sidebar_tts.py:430`、`listener_app/sidebar_tts.py:491`。
- TTS provider 私有配置已明确拆到独立 JSON，`create_tts_player()` 只从 `tts.provider + tts.config_path` 选择并读取独立文件；文档也明确要求不要把 provider 字段堆回 `listener.json`：`listener_app/sidebar_tts.py:1076`、`config/listener.md:149`、`docs/wechat-listening-pitfalls.md:305`。
- 运行时根目录与源码目录不是一回事。`ROOT_DIR` 指向运行时根目录，启动时会把 bundled `config/*.json` 复制到 runtime root 的 `config/`；当前已有原子写 JSON helper：`listener_app/sidebar_shared.py:34`、`listener_app/sidebar_shared.py:111`、`listener_app/sidebar_shared.py:147`。
- 当前仓库 `config/listener.json` 已经暴露出配置债务：DeepLX 开启但没显式写 `deeplx_url`，同时仍残留 `display.width`、`display.side` 旧字段；而文档已说明主路径不消费这类旧 UI 字段：`config/listener.json:19`、`config/listener.json:30`、`config/listener.md:124`、`config/listener.md:146`。
- Tauri 壳当前只暴露 `get_backend_connection_info`，没有“重启 managed backend”命令；backend sidecar 的 spawn / marker / ready wait 都在 Rust 侧 bootstrap 中：`desktop-shell/src-tauri/src/main.rs:18`、`desktop-shell/src-tauri/src/main.rs:36`、`desktop-shell/src-tauri/src/backend/bootstrap.rs:103`、`desktop-shell/src-tauri/src/backend/bootstrap.rs:542`。

## 方案结论

结论先写死：

- 第一阶段不做 backend 进程内热重载。
- backend 负责“配置读写 + 校验 + 返回 apply 策略”，不负责自杀式重启自身。
- Tauri 壳在 `managed=true` 且当前 shell 拥有 sidecar 时，负责“保存并应用”里的 sidecar 重启。
- 开发态或非托管态只提供“保存”并明确提示“需要手动重启 backend”，不伪装成已经生效。

### 1. 配置域划分

必须把配置拆成三层，禁止继续混：

- `listener.json`
  - 受支持字段：`translate.*`、`display.*`、`tts.provider`、`tts.config_path`，以及后续决定纳入 GUI 的 `listen.*`
  - 保存时保留未知字段，不能把旧字段或未来字段顺手抹掉
- provider 私有 JSON
  - `config/tencent_tts.json`
  - `config/doubao_tts.json`
  - 继续由 `tts.config_path` 选择
- 纯前端/运行态状态
  - `showOriginal`
  - `showStatusPanels`
  - 当前选中会话
  - header 上现有“朗读开关”运行态状态

`tts_auto_read_active_chat` 需要双重语义：

- 设置页里编辑的是“默认持久化配置”
- header 里的快开关仍然是“当前运行态 toggle”

否则用户一定会遇到“界面显示开着，但保存值和重启结果对不上”的一致性问题。

### 2. 配置 API 设计

backend 新增正式配置契约，至少包含：

- `GET /api/config`
  - 返回完整可编辑 DTO，而不是现在的残缺快照
  - DTO 必须显式区分：
    - 普通字段当前值
    - secret 字段是否已配置
    - 当前来源是 `config` / `env` / `missing`
    - 当前是否需要重启才能生效
- `PUT /api/config`
  - 接收完整或结构化 patch
  - 复用现有校验逻辑，失败时返回字段级错误
  - 保存采用原子写
  - 响应带回：
    - 已保存快照
    - `apply_strategy`
    - `restart_required`

`GET /api/config` 不应直接复用 `BackendRuntimeService.get_config_snapshot()`；应该新增独立的配置 DTO builder。

### 3. Secret / 环境变量处理

这块不能糊弄。直接把现有 secret 原文回显到前端，是坏设计。

第一阶段约束：

- `GET /api/config` 永远不回显 raw secret。
- secret / 类 secret 字段返回结构化状态，例如：
  - 是否已配置
  - 来源 `config` / `env` / `missing`
  - 当前 env key 名
  - 是否允许改写配置文件值
- `PUT /api/config` 对 secret 字段采用 write-only 语义：
  - 空值表示“保持现状”
  - 显式 `clear` 才表示清除配置文件值
  - 可以修改 `*_env` 字段
  - 可以输入新的明文配置值，但默认文案仍应推荐 env 方式

DeepLX URL 也按同样原则处理，因为当前 URL 很可能内嵌 key。

### 4. 保存与应用策略

#### 开发态 / 非托管态

- 前端点击“保存配置”
- backend 完成校验与落盘
- 前端显示“已保存，需手动重启 backend 才生效”
- 不提供伪 apply

判定依据：

- `backendInfo.managed === false`
- 或当前前端运行在非 Tauri 环境

#### Tauri 托管且 shell 拥有 sidecar

- 前端提供“保存并应用”
- 流程：
  1. `PUT /api/config` 成功
  2. 调用新的 Tauri command，例如 `restart_managed_backend`
  3. Rust 侧仅在 `ManagedBackendState` 真正 `owns_child=true` 时执行：
     - kill 现有 child
     - 清理匹配 marker
     - 使用同一 runtime root / config path 重新 spawn sidecar
     - 等待 `/healthz` ready
  4. 前端重走现有 hydrate / reconnect 链路

如果 `managed=true` 但当前状态不是 shell 自己拥有 child，而是复用已有 backend，也必须降级成“仅保存 + 提示手动重启”，不能乱杀外部进程。

### 5. 前端设置页形态

第一阶段不需要上复杂路由，建议在桌面壳 header 增加明确设置入口，落成抽屉或弹层即可。

设置页至少分三块：

- 翻译
  - `enabled`
  - `provider`
  - `deeplx_url`
  - `source_lang`
  - `target_lang`
  - `timeout_seconds`
- 显示
  - `english_only`
  - `tts_auto_read_active_chat`
  - `on_translate_fail`
- TTS
  - `provider`
  - `config_path`
  - provider-specific form

provider-specific form 必须按现有支持的 provider 分支渲染：

- `windows_system`
  - 当前无独立配置文件时，表单只需展示“无额外参数”
- `doubao`
  - 覆盖现有独立 JSON 支持字段
- `tencent_cloud`
  - 覆盖现有独立 JSON 支持字段

不要只做腾讯云专属表单，否则 `tts.provider` 一切到别的 provider，设置页就成半残。

## 约束

- `listener.json` 与 provider 私有 JSON 的边界不能破。
- 保存逻辑必须原子写，并保持 LF。
- 保存逻辑必须保留未知字段，避免误删旧字段或未来字段。
- 现有 fail-fast 校验不能被 GUI 绕过去；GUI 只是入口变了，不是降低约束。
- managed apply 不能杀掉外部 backend；只有 shell 自己拥有的 child 才允许重启。
- `/healthz`、`/api/runtime`、`/api/sessions`、`/events` 现有契约不能因为配置页顺手漂移。
- 任何 `config/listener.json` 字段新增、删除或语义变更，都要同步更新 `config/listener.md`。
- 任何监听、健康契约、打包或 TTS 相关改动，都要同步更新 `docs/wechat-listening-pitfalls.md`。

## 验收标准

1. 桌面壳存在正式设置入口，用户不再需要直接编辑 JSON 才能配置 DeepLX / TTS。
2. `/api/config` 能返回完整、安全、可编辑的 DTO，而不是当前残缺快照。
3. 保存配置时，`listener.json` 与 provider 私有 JSON 会按各自边界落盘，且未知字段不会被误删。
4. secret 字段不会被明文回显，但用户仍可通过 write-only 方式更新或切换 env key。
5. 开发态或非托管态保存后，UI 会明确提示“需要手动重启 backend”；不会假装已经生效。
6. Tauri 托管且 shell 拥有 sidecar 时，`保存并应用` 可以通过重启 managed backend sidecar 生效，而不需要用户关闭整个应用。
7. header 现有运行态“朗读开关”继续工作，且与设置页里的默认值语义不冲突。
8. 文档与实现保持一致，`config/listener.md`、`docs/wechat-listening-pitfalls.md` 同步更新。

## 风险与降级

- 最大风险不是表单，而是 managed backend restart。如果这条链路不稳，先降级成“托管态也只保存并提示重开应用”，不要硬交半成品。
- secret 处理如果偷懒做成明文回显，后面几乎必然返工；这块必须一开始就定成 write-only + source metadata。
- 若保存逻辑按“重建整个 JSON”实现，很容易把当前 tolerated 的旧字段或未来字段顺手抹掉；必须基于 raw config merge。
- 如果实现阶段发现需要新增大量跨语言 schema 同步成本，应优先把 schema owner 继续收在 Python 侧，再把前端当消费者；不要复制一套 TS 常量当真理源。
