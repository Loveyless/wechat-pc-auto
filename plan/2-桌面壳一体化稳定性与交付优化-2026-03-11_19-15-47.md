# Plan：桌面壳一体化稳定性与交付优化

## 任务概述

当前 `desktop-shell/` 已经具备 Tauri 一体化桌面壳能力：

- `npm run tauri dev` / `npm run tauri build` 会先构建 Python sidecar
- Tauri 壳会自动托管 `wechat-auto-backend.exe`
- backend 会继续拉起 `group_listener_worker.exe`

但“能跑”不等于“够稳、够好交付、后续好维护”。
本计划只覆盖当前主路径的硬化项，不讨论旧 Tk 回退路径重构。

## 当前仓库事实

- Tauri backend bootstrap、Windows mutex、pid/start_token marker、health probe 都集中在 `desktop-shell/src-tauri/src/main.rs`
- 壳启动等待时间固定为 `BACKEND_READY_TIMEOUT_SECONDS=15`：`desktop-shell/src-tauri/src/main.rs`
- 当前 `probe_backend_health()` 通过字符串包含 `{"status":"ok"}` 判定健康，但 `runtime_api.py` 实际返回的是 `{"status": "ok"}`；也就是说，ready 判定当前存在实现级 bug，不只是体验问题
- sidecar 构建脚本是 `scripts/build_desktop_shell_sidecars.py`
- 当前 sidecar 构建脚本只显式收集了 `websockets` 和 `tencentcloud`：`scripts/build_desktop_shell_sidecars.py`
- Python 依赖声明只有：
  - `uiautomation`
  - `websockets`
  - `tencentcloud-sdk-python-tts`
  - 见 `requirements.txt` 和 `pyproject.toml`
- `.env.local` 读取逻辑已经存在，并按“运行时目录优先、可执行目录兜底”执行：`listener_app/sidebar_shared.py`
- 桌面前端没有测试脚本：`desktop-shell/package.json`
- Python 后端已有单元测试目录：`tests/`
- 当前 Tauri 壳没有 single-instance 机制：
  - `desktop-shell/src-tauri/Cargo.toml` 未引入 single-instance plugin
  - `desktop-shell/src-tauri/src/main.rs` 只在退出时做 child 清理

## 本阶段目标

把当前桌面壳从“可以交付”推进到“更稳地交付、更容易维护、更容易排障”。

不做的事：

- 不重写 Python backend
- 不改监听主链路的 `session-only + preview-only` 契约
- 不把秘密配置烘焙进安装包
- 不做跨平台

## 优先级

### P0：修正 health probe 解析与 backend ready 判定

#### 问题

当前 Tauri 壳的 `probe_backend_health()` 用固定字符串匹配 `{"status":"ok"}` 判定 backend 是否 ready。
但 Python API 实际返回的是默认 JSON 序列化结果 `{"status": "ok"}`，中间有空格。

这不是“偶尔慢一点”的体验问题，而是现有 ready 判定逻辑本身就不正确。
在这个 bug 没修掉之前，后面的“显式化冷启动状态”很容易沦为给错误状态机贴创可贴。

#### 目标

- 让 backend ready 判定基于正确、稳定的协议，而不是脆弱的字符串猜测
- 消除当前 15 秒超时和 `still starting` 日志里的假阳性

#### 建议改动

- 修正 `desktop-shell/src-tauri/src/main.rs` 中的 health probe 解析逻辑
- 优先按 HTTP 状态码 + JSON 解析结果判定，而不是裸字符串包含
- 如有必要，为 `/healthz` 定义更稳定的最小契约，并让壳端只依赖该契约

#### 最小验证

- 冷启动 release 壳
- 确认 backend 真正 ready 后，壳端不会继续错误记录 `still starting`
- `desktop-shell-bootstrap.log` 中的 ready 日志与实际 `/healthz` 返回一致

### P0：补齐 sidecar 打包依赖完整性

#### 问题

当前 sidecar 构建脚本只对已知动态依赖做显式收集：`websockets` 和 `tencentcloud`。
仓库当前没有 `requests` 依赖链的直接使用证据；把风险硬绑到 `requests` 上会把错误事实写进方案。
真正的问题是：sidecar 打包口径还没有被表述成“按真实运行期依赖与 hidden imports 收敛”，后续一旦新增动态导入或打包态依赖，仍可能因为口径漂移而踩坑。

#### 目标

- sidecar 的真实运行期依赖与 hidden imports 必须显式、可复现
- 构建结果不能依赖“某台机器恰好装过某个包”
- 源码态依赖、PyInstaller 收集策略与 smoke test 口径一致

#### 建议改动

- 先盘清 backend / worker 的真实运行期依赖清单，区分“普通 import 可自动收集”和“动态导入需显式 hidden import”
- 仅对真实需要的运行期依赖补 `requirements.txt` / `pyproject.toml` 与 `scripts/build_desktop_shell_sidecars.py`
- 保持源码态依赖检查、PyInstaller 收集策略与打包后 smoke test 口径一致

#### 最小验证

- 重新执行 `python scripts/build_desktop_shell_sidecars.py`
- 重新执行 `cd desktop-shell && npm run tauri build`
- 直接运行 release 壳，确认 backend sidecar 启动链路无依赖缺失

### P1：把 backend 冷启动状态显式化，去掉“先报 reconnecting 再自愈”的糙感

#### 问题

当前壳侧以固定 15 秒等待 backend ready。
如果 backend 在超时后才 ready，前端会先进入 `reconnecting`，再恢复。
这虽然不一定算故障，但用户体感就是“壳一打开就像坏了”。

前提要说清楚：这一项必须建立在“health probe 判定已经正确”的基础上。
否则你分出来的“启动中 / 启动失败 / 已连接”本身就是错的。

#### 目标

- 把 backend 启动中作为明确状态，不再混进“连接失败”
- 降低冷启动误报和状态闪烁

#### 建议改动

- 重新定义 `desktop-shell/src-tauri/src/main.rs` 的 backend 启动状态输出
- 在 `desktop-shell/src/lib/api.ts` 与 `desktop-shell/src/hooks/use-desktop-shell.ts` 中区分：
  - backend 正在启动
  - backend 启动失败
  - backend 已连接
- 如有必要，把 health 就绪点前移，或提供独立启动状态命令

#### 最小验证

- 冷启动 release 壳
- 确认前端优先显示“启动中”而不是直接 `reconnecting`
- backend ready 后状态应平滑进入 `ready`

### P1：拆分 Tauri bootstrap 模块，降低 `main.rs` 维护成本

#### 问题

当前 `desktop-shell/src-tauri/src/main.rs` 同时承担：

- Win32 mutex
- pid/start_token 标记
- health probe
- sidecar spawn
- bootstrap 日志
- child 生命周期清理

这不是合理的长期形态。

#### 目标

- 把 Tauri bootstrap 逻辑拆成可理解、可测试的模块
- 让后续修改启动流程时，影响面可控

#### 建议改动

- 拆出独立模块：
  - `backend_bootstrap_lock`
  - `backend_marker`
  - `backend_launcher`
- 让 `main.rs` 只保留 Tauri builder、plugin 注册和顶层编排

#### 最小验证

- `cargo fmt`
- `cd desktop-shell && npm run tauri build`
- 若拆出纯函数，补对应 Rust 单测

### P1：补桌面壳自动化测试，别再只靠手工验

#### 问题

- Python 侧已有 `tests/`
- 桌面前端没有 `test` 脚本
- Tauri bootstrap 也没有单测或自动 smoke test

当前回归方式主要靠人工构建和人工点壳，不够硬。

#### 目标

- 前端连接层要有自动回归
- Tauri bootstrap 关键逻辑要有最小自动验证
- release 壳要有最小 smoke test

#### 建议改动

- 给 `desktop-shell/package.json` 增加测试脚本
- 为下列模块补测试：
  - `desktop-shell/src/lib/api.ts`
  - `desktop-shell/src/hooks/use-desktop-shell.ts`
- 为 Tauri bootstrap 的纯逻辑补 Rust 单测
- 增加“构建 release 后启动壳并探测 `/healthz`”的 smoke test

#### 最小验证

- 前端测试命令可执行
- Rust 单测可执行
- release smoke test 可在本机稳定通过

### P2：把 shell 收敛为 single-instance

#### 问题

当前 backend 已经通过 mutex + pid/token 避免重复 spawn。
但 shell 本身仍允许多开；这会带来：

- 多个窗口同时连同一个 backend
- 用户对“当前到底哪个窗口算主窗口”产生混淆

这不是立刻阻断的 bug，但交互语义不清。

#### 目标

- 桌面壳收敛为单实例
- 第二次启动只激活已有窗口，不再制造“多个窗口连同一个 backend”的歧义

#### 建议改动

- 在 Tauri 壳引入 single-instance 机制
- 第二次启动时只激活已有窗口，不再新建第二个壳窗口
- 不得影响已有 backend sidecar 复用逻辑与 mutex / marker 约束

#### 最小验证

- 双击启动第二次时，行为必须稳定且可预期
- 不得影响已有 backend sidecar 复用逻辑

## 推荐执行顺序

1. P0：修正 health probe 解析与 backend ready 判定
2. P0：补齐 sidecar 打包依赖完整性
3. P1：显式化 backend 冷启动状态
4. P1：拆分 Tauri bootstrap 模块
5. P1：补桌面壳自动化测试
6. P2：把 shell 收敛为 single-instance

## 迁移 / 回滚 / 降级策略

本计划的回滚优先级必须固定，禁止到发布时再临场拍脑袋：

1. 若 P0 / P1 / P2 任一改动导致 `npm run tauri build`、release 壳冷启动、`/healthz` 探测或前端连接状态出现回归，先阻断分发，不发布带回归的 Tauri 壳。
2. 代码层回滚优先回退到“当前 `backend_main.py + desktop-shell/` 主路径的已验证基线”，而不是把旧 Tk 路径重新抬回正式主路径。
3. `listener_app/sidebar_translate_listener.py` 只保留为开发期回退和排障对照；它可以帮助定位问题，但不作为这轮桌面壳交付的正式降级方案。
4. 若仅 Tauri 壳托管链路回归，但本地后端与 HTTP / WebSocket 契约仍正常，允许临时退回源码态验证路径：`backend_main.py + npm run dev`，用于内部验证与排障，不视为正式交付完成。

## 交付标准

满足以下条件，才算本计划完成：

- `npm run tauri build` 稳定通过
- backend ready 判定与 `/healthz` 实际返回一致，不再依赖脆弱字符串匹配
- release 壳冷启动状态表现清晰，不再把“backend 启动中”误报成连接故障
- sidecar 依赖链明确，不靠环境侥幸
- Tauri bootstrap 不再是超大单文件黑盒
- 新桌面链路具备最小自动化回归
