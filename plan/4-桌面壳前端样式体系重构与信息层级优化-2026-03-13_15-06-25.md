# Plan：桌面壳前端样式体系重构与信息层级优化

## 任务概述

当前 `desktop-shell` 的运行契约、健康检查、CI 和发布闸口已经基本收口，继续优先折腾后端边界，收益会明显下降。
现在最值得动的是前端表现层：不是再堆功能，而是把桌面壳从“能看状态的开发页”升级成“信息层级清楚、状态表达可靠、视觉有辨识度的正式桌面 UI”。

这份计划只覆盖前端样式、布局、信息架构和前端组件拆分建议。
结论先说死：**可以改，而且应该单独开刀；但第一期只改视觉系统和信息层级，不碰 Python runtime、本地 API 契约和打包链。**

## 当前仓库事实

- 前端入口非常薄：
  - `desktop-shell/src/App.tsx` 只挂载 `DesktopShell`
- 当前主页面几乎全部堆在一个组件里：
  - `desktop-shell/src/components/shell/desktop-shell.tsx`
  - 里面同时塞了 header、会话列表、消息流、状态摘要
- 当前视觉系统非常薄，而且明显偏“默认深色后台模板”：
  - `desktop-shell/src/index.css`
  - 主题是深蓝黑底 + 青蓝主色
  - 字体栈仍然接近默认 `Inter / Segoe UI / 微软雅黑`
- 当前通用 UI 原子组件只有两块：
  - `desktop-shell/src/components/ui/button.tsx`
  - `desktop-shell/src/components/ui/status-badge.tsx`
- 当前状态和数据来源已经足够完整，前端不缺信息，只缺表达：
  - `desktop-shell/src/hooks/use-desktop-shell.ts`
  - 已有 `connectionState`
  - 已有 `runtimeState`
  - 已有 `translationState`
  - 已有 `ttsState`
  - 已有会话列表和消息流
- 当前桌面壳已经不是 Tk 替身，而是真正的主 UI：
  - `README.md`
  - `docs/desktop-shell-build.md`

## 当前界面问题

### 1. 视觉方向过于通用

现在的界面是典型“深色 + 发光蓝 + 圆角卡片”的默认后台审美。
这不算错，但太像临时开发面板，没有产品辨识度，也没有把“微信监听 / 翻译 / 朗读 / runtime 健康”这些特征做出来。

### 2. 信息层级不清楚

当前 header、状态条、会话列表、消息流都在用接近的卡片强度和视觉重量。
结果不是“信息丰富”，而是“信息全在抢前景”，用户很难一眼看出：

- backend 现在到底是 `ready`、`starting` 还是 `degraded`
- 当前会话和其他会话的主次关系
- 消息正文、翻译结果、原始预览、capture level 的优先级
- TTS / translation 状态到底是系统状态还是消息级状态

### 3. 状态表达不够锋利

现在 `StatusBadge` 只有 `primary / neutral / accent` 三种 tone：
- `desktop-shell/src/components/ui/status-badge.tsx`

这不够用。`ready`、`starting`、`startup_failed`、`degraded`、`reconnecting` 的风险级别完全不同，结果现在视觉差异太弱。
这会把“健康契约已经收口”的价值浪费掉。

### 4. 会话列表和消息流都还是“卡片堆”

当前会话列表是一排排同权重按钮卡片，消息流也是一张张结构接近的卡片：
- `desktop-shell/src/components/shell/desktop-shell.tsx`

这类布局写起来省事，但长期看有两个坏结果：
- 可扫描性差
- 一旦消息多、状态多，就会变成视觉噪音墙

### 5. 缺少真正的空态 / 错误态 / 降级态设计

现在连接层已经能区分：
- `loading`
- `starting`
- `ready`
- `startup_failed`
- `degraded`
- `reconnecting`

但页面层没有围绕这些状态做明确的视觉落点。
这会让“契约是清楚的，界面却不像清楚的”。

## 目标

- 建立一个桌面壳可持续扩展的前端视觉系统，而不是继续靠局部 class 拼页面
- 让 runtime 健康状态、会话导航和消息阅读成为三个清晰层级
- 让 `starting / ready / degraded / startup_failed / reconnecting` 有明确且一致的视觉表达
- 让消息展示更适合“预览监听 + 翻译学习”这个真实场景，而不是 generic admin feed
- 在不改后端契约的前提下，提高前端的完成度和辨识度

## 不做的事

- 不改 `/healthz`、`/api/runtime`、`/api/sessions`、WebSocket 事件契约
- 不为前端样式改造重新设计 runtime 状态机
- 不在第一期同时做“新视觉 + 新交互语义 + 新功能”
- 不在第一期同时支持两套主题（浅色 / 深色）并行
- 不为了样式改造引入新的大型组件库迁移

## 推荐视觉方向

### 推荐方案：Light Ops Desk（浅底运行台）

推荐把当前默认深色开发面板，改成**浅底运行台风格**：

- 主背景不是纯白，而是带一点纸感或雾感的浅暖灰
- 主卡面是高对比浅面板，辅以少量深色信息块
- 运行状态用明确的功能色：
  - `ready`：青绿
  - `starting`：琥珀
  - `degraded`：橙色
  - `startup_failed`：红色
  - `reconnecting`：蓝灰
- 正文阅读区优先可读性，不做“发光赛博屏”
- 数据标签、时间、capture level 使用窄字重或等宽信息字体，和正文层分开

为什么推荐这个方向：

- 当前仓库已经长期处在深色开发风格，继续加深只会更像内部工具
- 这是一个要长时间盯着看的桌面壳，不是 landing page
- 浅底更适合把“消息正文”和“运行状态”拆层，不会全糊在一片暗色里

### 不推荐方案：继续沿用深色青蓝模板

这个方向最省事，但坏处也最明显：

- 太像任何一个默认后台模板
- 卡片、边框、徽标会越来越像一坨
- 状态严重性很难拉开层次

结论：**别再续写现在这套深色青蓝默认盘。**

## 样式优化建议

### P0：先建立语义化视觉 token，而不是继续堆 Tailwind 类

建议先重构 `desktop-shell/src/index.css` 的主题变量，不要再只维护：
- `background`
- `card`
- `primary`
- `accent`

建议至少补成下面这类语义层：

- `canvas`：整页底色
- `panel`：主面板
- `panel-muted`：次级面板
- `panel-elevated`：高优先级浮层 / 关键状态块
- `text-primary`
- `text-secondary`
- `text-tertiary`
- `state-ready`
- `state-starting`
- `state-degraded`
- `state-failed`
- `state-reconnecting`
- `session-selected`
- `message-preview-only`

原因：
- 当前变量更像颜色桶，不像设计系统
- 不先抽语义 token，后面每个组件都会自己长出一套颜色判断

### P0：把页面拆成“运行总览 / 会话导航 / 消息阅读”三层

当前 `desktop-shell.tsx` 应该拆组件，不然样式重构会越来越脏。

建议至少拆成：

- `shell-header`
- `runtime-status-rail`
- `session-list-pane`
- `session-list-item`
- `message-stream-pane`
- `message-card`
- `empty-state-panel`
- `error-state-panel`

推荐结构：

1. 顶部：运行总览条
   - backend 地址
   - 连接状态
   - worker 状态
   - translate / tts 可用性

2. 左侧：会话导航
   - 更像列表导航，不要像一墙按钮卡片
   - 突出当前选中、未读数、最新预览、更新时间

3. 右侧：消息阅读区
   - 强调正文
   - 降低“原始预览”“capture level”“时间戳”的视觉权重

### P0：状态徽标要从“三色 pill”升级成真正的状态系统

`status-badge.tsx` 现在过于单薄。
建议改成：

- 支持更多 tone：
  - `success`
  - `warning`
  - `danger`
  - `info`
  - `muted`
- 支持 size：
  - `sm`
  - `md`
- 支持 emphasis：
  - `soft`
  - `solid`
  - `outline`

并明确映射：

- `ready` -> `success`
- `starting` -> `warning`
- `startup_failed` -> `danger`
- `degraded` -> `warning` 或 `danger-soft`
- `reconnecting` -> `info`
- `preview_only` -> `muted`

### P1：会话列表别再用大圆角等权卡片

当前列表项太像“块按钮”，不利于快速扫读。

建议改成：

- 更扁的列表项
- 左侧保留会话类型或状态标记
- 中间是名称 + 预览
- 右侧是未读数 + 时间
- 选中项用侧边条、底色或更强对比突出，不要只靠淡蓝描边

另外建议把“群聊 / 私聊”从当前高频 pill 弱化成更轻的 secondary meta，不要抢正文。

### P1：消息卡要围绕“阅读”而不是“元数据展示”

当前消息卡的优先级是平的，导致：
- 发送人
- 时间
- capture level
- 正文
- 原始预览

几乎都在抢视线。

建议改成：

- 第一层：译文 / 当前展示文本
- 第二层：原始预览
- 第三层：发送人、时间、capture level

并增加两类视觉区分：

- `pendingTranslation=true`：显式 loading skeleton 或进度态
- `captureLevel=preview`：给出轻量提示，不要和错误态混在一起

### P1：做明确的系统态页面，而不是把错误都塞进右上角信息块

至少要有这些独立状态设计：

- `loading`
- `starting`
- `startup_failed`
- `degraded`
- `reconnecting`
- `no session selected`
- `no messages`

现在这些状态都有数据层支持，但 UI 表达不够像“系统状态”。
建议做成明确的面板，不要只靠一行小字说明。

### P2：补真正有意义的动效

建议只做少量、有方向的动效：

- 页面初次进入的分层淡入
- 会话切换时的选中高亮滑动
- 状态切换时 badge / rail 的短促过渡
- 新消息进入时轻量位移动效

不建议做：

- 大面积玻璃拟态漂浮
- 到处 pulse
- 长时间 shimmer

原因很简单：这不是营销页，是运行台。

### P2：把字体策略从“默认系统字”升级到有角色分工

当前字体太像默认后台模板。
建议做成两层：

- 正文 / 中文界面：更稳的 UI 字体
  - 例如 `IBM Plex Sans`, `PingFang SC`, `Microsoft YaHei`
- 数据 / 时间 / capture level / URL：
  - 例如 `JetBrains Mono`, `Cascadia Code`

不一定非得上远程 webfont，但必须让“正文”和“状态数据”在气质上分开。

## 组件与代码组织建议

### 建议保守拆分，不碰数据层

第一期推荐只重构这些文件：

- `desktop-shell/src/components/shell/desktop-shell.tsx`
- `desktop-shell/src/components/ui/button.tsx`
- `desktop-shell/src/components/ui/status-badge.tsx`
- `desktop-shell/src/index.css`

并新增更细组件，例如：

- `desktop-shell/src/components/shell/shell-header.tsx`
- `desktop-shell/src/components/shell/runtime-status-rail.tsx`
- `desktop-shell/src/components/shell/session-list-item.tsx`
- `desktop-shell/src/components/shell/message-card.tsx`

第一期不建议主动改：

- `desktop-shell/src/hooks/use-desktop-shell.ts`
- `desktop-shell/src/lib/api.ts`
- `desktop-shell/src/lib/shell-types.ts`

理由：
- 现在连接层和契约层已经稳定
- 样式改造应该是“消费现有状态”，不是顺手重写状态逻辑

## 推荐执行顺序

1. 先定视觉方向和 token
2. 再拆页面层组件
3. 再改会话列表和消息阅读区
4. 再补空态 / 错误态 / 降级态
5. 最后做细节动效和按钮/徽标 polish

这个顺序不能反。
你如果先画漂亮卡片，不先收视觉 token，后面一定会变成全项目散落 class 的垃圾堆。

## 验收标准

满足以下条件，才算这次前端样式改造完成：

- 页面视觉方向明确，不再像通用深色后台模板
- 顶部运行状态、左侧会话导航、右侧消息阅读三层清晰可扫
- `starting / ready / degraded / startup_failed / reconnecting` 视觉表达稳定且一眼可分
- 会话选中态、未读态、预览态和消息 pending 态都有明确设计
- 样式改造不引入后端契约漂移
- 代码结构不再把整个页面堆在一个大组件里

## 最小验证

- `cd desktop-shell && npm test`
- `cd desktop-shell && npm run build`
- `cd desktop-shell/src-tauri && cargo test`

手工验证至少覆盖：

- `ready`
- `starting`
- `startup_failed`
- `degraded`
- `reconnecting`
- 空会话
- 空消息
- 窄窗口宽度下的布局可用性

## 我的推荐结论

前端样式可以开始，而且建议**单独立项、只做前端**。

第一期最值钱的不是“多加几个发光按钮”，而是三件事：

- 视觉系统 token 化
- 信息层级重构
- 系统状态可视化

如果这三件事不先做，后面再加功能，界面只会越来越像调试页，不会越来越像产品。
